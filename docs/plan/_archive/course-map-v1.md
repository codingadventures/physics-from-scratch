# Build a 2D Physics Engine: Course Map

Status: **draft for approval**. No code or blog scaffold exists yet.

## 1. Goal

A 2D rigid body engine in TypeScript that simulates 2..N bodies and collides circles, boxes, and static planes, with a basic impulse solver. Stacking, determinism, performance, and the Rust/C++ port are deferred to an advanced track.

The course is built by one learner (Gio, the guinea pig) and published as a public blog. Each lesson is drafted here; Gio writes the posts from his own experience.

## 2. Prerequisites (stated, not taught)

- Vectors, dot/cross product, matrices, basic trigonometry.
- Rotations (2D is enough for this course).
- Basic calculus intuition: velocity is the derivative of position.
- Programming experience (C++ or similar). TypeScript is covered in Module 0.

## 3. Format

| Element | Rule |
|---|---|
| **Pill** | One lesson page, 5-7 minutes to read. One idea each. |
| **Checkpoint** | Every pill ends with 1-2 "can you answer this?" questions (no code). |
| **Exercise** | After every 3-4 pills. Implement stubs in the starter repo until the tests pass. |
| **Demo** | Each module ends with a debug-draw demo in the browser (the visual check tests can't give). |
| **Interactive visual** | Math-heavy pills embed a live visual (step through, scrub, drag shapes). See section 12. |
| **Reading list** | Each pill links 1-3 sources, split into *essential* and *deeper*. |

Time estimates below are guesses and assume some prior physics and game-dev experience; someone new to TypeScript and physics should expect noticeably longer (plan on 1.5-2x). Gio logs real time per pill and exercise, and the estimates get recalibrated for the blog.

### Repo model

Full skeleton spec: section 11.

- Starter repo: every exercise is a stub with a fixed signature that throws `TODO`, and failing tests already exist.
- Solutions live separately (a `solutions` branch), validated against every test before publishing.
- Stack: TypeScript, Vite, Canvas 2D renderer (scaffolded once, ~150 lines, with debug draw for contacts, normals, AABBs), Vitest.

### Test kinds

1. **Pure math/geometry**: exact in/out (overlap tests, manifolds).
2. **Behavioral**: fixed timestep with tolerances (a ball rests at `y = r`, energy never grows).
3. **Visual**: no test, covered by the module demo.

## 4. Standard track

Stage names follow Gio's pipeline. "Gathering" means gathering the rigid bodies every frame: collecting each body's current transform, world-space AABB, and the per-step data the later stages consume.

### Module 0: Setup and TypeScript for C++ developers (~1.5h)

| Pill | Topic |
|---|---|
| 0.1 | Course overview and the final demo |
| 0.2 | TypeScript for C++ developers: types, classes, interfaces, modules, no pointers |
| 0.3 | Project tour: Vite, Vitest, the renderer, running a test |
| 0.4 | Vector math utilities and the debug draw API |
| 0.5 | How to read the interactive visuals (step, scrub, drag) |

**Exercise 0:** implement `Vec2` operations (add, dot, cross, normalize, perp). Tests: algebraic properties and edge cases (zero-length normalize).

### Module 1: Rigid body representation (~3h)

| Pill | Topic |
|---|---|
| 1.1 | What a rigid body is: state (position, angle, linear/angular velocity) |
| 1.2 | Mass, inverse mass, static bodies (inverse mass 0) |
| 1.3 | Moment of inertia for circles and boxes |
| 1.4 | Integration: explicit vs semi-implicit Euler, and why we pick one |
| 1.5 | The game loop and the fixed timestep |
| 1.6 | Shapes: circle, box, plane, and their local/world transforms |

**Exercise 1:** `Body`, shape definitions, `integrate(dt)`. Tests: free fall matches the analytic result within tolerance; constant angular velocity; static bodies never move; inertia values.

**Demo 1:** bodies falling and spinning through nothing.

### Module 2: Gathering, the world and step pipeline (~2h)

| Pill | Topic |
|---|---|
| 2.1 | The pipeline at a glance: integrate, find pairs, find contacts, solve |
| 2.2 | The `World`: registering bodies and gathering them every frame |
| 2.3 | World-space AABBs for rotated shapes |
| 2.4 | Per-step data: pair lists and contact lists, avoiding allocation churn |

**Exercise 2:** `World.step(dt)` scaffolding and `computeAABB(body)`. Tests: rotated box AABB correctness; step order; bodies removed cleanly.

### Module 3: Broadphase (~2h)

| Pill | Topic |
|---|---|
| 3.1 | Why broadphase exists: O(n²) and what it costs |
| 3.2 | Brute-force AABB overlap pairs (our baseline) |
| 3.3 | Sort and sweep along one axis |
| 3.4 | Pair filtering: static-static, same body, collision groups |

**Exercise 3:** implement brute-force and sort-and-sweep behind one `Broadphase` interface. Tests: both produce identical pair sets on randomized scenes; static-static pairs excluded.

**Demo 3:** AABB overlaps highlighted live.

### Module 4: Narrowphase (~5h)

| Pill | Topic |
|---|---|
| 4.1 | Manifolds: normal, penetration depth, contact points |
| 4.2 | Circle vs circle |
| 4.3 | Circle vs plane (half-space) |
| 4.4 | Box vs plane |
| 4.5 | Circle vs box (closest point on the box) |
| 4.6 | Box vs box: the separating axis test, used as a recipe |
| 4.7 | Box vs box: finding the reference/incident face and clipping |
| 4.8 | Dispatching: a shape-pair table |

**Exercise 4a (pills 4.1-4.5):** circle/plane/box manifolds. Tests: known-answer cases, normal direction convention, symmetry (A vs B mirrors B vs A).
**Exercise 4b (pills 4.6-4.8):** box-box via the recipe. Tests: separated, touching, face-face, corner-edge, rotated.

**Demo 4:** drag bodies around and see contact points and normals.

### Module 5: Collision response (~5h)

| Pill | Topic |
|---|---|
| 5.1 | Relative velocity at a contact point |
| 5.2 | The normal impulse (linear only), derived and applied |
| 5.3 | Adding rotation: lever arms and effective mass |
| 5.4 | Restitution (bounciness) |
| 5.5 | Friction: tangent impulse and the Coulomb cone |
| 5.6 | Iterating over contacts (a basic sequential impulse loop) |
| 5.7 | Fixing penetration: positional correction and slop |
| 5.8 | What this solver gets wrong, honestly (jitter, sinking, no stacking) |

**Exercise 5a:** linear normal impulse. Tests: equal-mass 1D collision exchanges velocity; restitution 0 and 1 behave as expected; momentum conserved.
**Exercise 5b:** angular response and friction. Tests: off-center hit induces spin; friction stops a sliding box on a plane; energy never increases.
**Exercise 5c:** iteration and positional correction. Tests: a ball dropped on a plane settles; no tunnelling at normal speeds; penetration stays under a threshold.

### Module 6: Capstone (~2h)

| Pill | Topic |
|---|---|
| 6.1 | Putting it together: scenes (ball pit, ramp, box drop) |
| 6.2 | A debug toolkit: pause, step, slow-mo, contact inspector |
| 6.3 | Retrospective: what you built and what's missing |

**Demo 6:** the full engine running three scenes.

**Standard track total (estimate): about 20h**, with 36 pills and 9 exercises.

### Conventions (locked)

| Topic | Convention |
|---|---|
| Units | metres, seconds, kilograms, radians |
| Axes | y up in the world; the renderer flips for the canvas |
| Rotation | counter-clockwise positive |
| Vectors | plain `{ x, y }` objects and free functions (`add(a, b)`), no operator tricks, no mutation. Allocation cost is ignored on purpose (correctness over performance). |
| Static body | inverse mass 0 and inverse inertia 0 |
| Plane | unit `normal` and `offset d`; the solid half-space is `dot(normal, p) <= d` |
| Manifold normal | unit vector pointing from body A to body B |
| Penetration | positive depth when overlapping |
| Timestep | fixed `dt = 1/60` in all behavioral tests |
| Tracing | optional ambient `trace` module, no-op by default, never required by tests or exercise signatures |
| Float tolerance | `expectClose(a, b, 1e-6)` for geometry, looser for simulated results |

### Solutions policy (proposal)

Every exercise ships with a published solution so a stuck learner can see it and carry on. Two tracks keep this honest:

1. **Test oracle (hidden):** I write a reference solution for each exercise, used only to validate tests before they ship. Gio does not read it before attempting the exercise, since he is the first learner.
2. **Published solutions:** Gio's own passing solutions become the public ones, with a short "what I did and why" note per exercise. Where his approach differs from the reference, the difference is blog material.
3. **Until Gio finishes a module,** the `USE_REF=1` switch uses the reference implementation so later modules aren't blocked. It is replaced by Gio's version once he has completed the module.

**Hint ladder per exercise** (before the solution): (1) a nudge about where to look, (2) the approach in words, (3) pseudocode, (4) the full solution. Most stuck points need hint 1 or 2, and it keeps the solution from being the first thing a learner reaches for.

**Quality gate:** a solution is only published if it passes every test, including behavioral ones at the fixed timestep. A learner's solution that passes but is fragile gets a note explaining the limitation, not silent approval.

### Known risks

1. **Exercise dependencies:** later tests use earlier exercises (everything needs `Vec2`). A learner stuck on Exercise 0 is blocked everywhere. Mitigation: see the solutions policy above. An environment switch (`USE_REF=1`) that swaps stubs for reference implementations, exercise by exercise, so a learner can skip ahead without being blocked.
2. **Wrong or over-tight tests:** every test is validated against the reference solution before shipping, and behavioral tolerances are tuned on it.
3. **API churn:** the contract above is frozen once lessons are written, because lessons quote signatures.

## 12. Interactive visual layer

**Problem:** formulas like SAT or the impulse equation are hard to absorb without seeing what each term does. The course needs visuals that unfold the algorithm, in the spirit of a debug draw that steps through a loop one iteration at a time.

**Can it live on a static GitHub site?** Yes. Interactive visuals are client-side JavaScript drawing to a canvas, and GitHub Pages serves static files, including JavaScript. The build step (Vite or Astro) compiles TypeScript to static assets. Only server-side features (accounts, saved progress) are out, and those are the future website you mentioned.

### Core idea: algorithms emit a trace, visuals replay it

1. Algorithms call an optional ambient `trace` (no-op by default): `trace.step("project A onto axis n0", [draw primitives])`.
2. A **recorder** collects the steps into a list of frames: label, drawn primitives, and the values at that moment.
3. A **player widget** replays them: play, pause, step forward/back, scrub.
4. The same code runs in the engine (live debug draw), in the tests (trace off), and in the blog (replayed).

Consequences:

- **No divergence:** the visual cannot disagree with the maths, because it is the real algorithm.
- **Time travel:** stepping backwards and scrubbing come free from recording.
- **One mechanism** serves the lessons, the learner's own debugging, and the engine's debug draw.
- **Learner cost is near zero:** exercise signatures don't change. A learner's own solution shows up in the visuals if they add `trace.step` calls, and the starter repo's demos do this in the reference code.

### Widget types

| Type | What it does | Example use |
|---|---|---|
| **Step-through** | Replays a recorded trace with play/step/scrub | SAT axis by axis; face clipping; one solver iteration at a time |
| **Drag and see** | Shapes you can drag, with live normal, depth, contacts | Circle vs box closest point; manifold updating as you move |
| **Formula-linked** | Hovering a term in an equation highlights its geometry | In the impulse formula, hover the relative velocity term and see that vector |
| **Parameter play** | Sliders for restitution, friction, iterations, timestep | Bounce height vs restitution; jitter vs iteration count |
| **Simulation recorder** | Records a whole sim, then scrub back and forth | The engine's own debug tool and the Module 6 capstone |

### Site stack (recommendation)

- **Astro with MDX** for the blog: static output that deploys to GitHub Pages, and interactive components embed as "islands" that only load JavaScript where used. Content stays Markdown.
- Visual widgets are plain TypeScript with Canvas 2D, sharing the engine source, no framework dependency.
- Respect `prefers-reduced-motion`, and keep a static image fallback per visual.
- **Uncertainty:** I'm confident about this approach but haven't yet checked the current Astro and GitHub Pages deployment steps. I'll verify against the official docs when building the scaffold, and fall back to plain Vite plus Markdown if Astro is awkward.

### Cost and risk

- The framework (recorder, player, drag helpers) is built once. Each visual is then roughly an hour or two of authoring. With about 20 visuals, this is meaningful work, and the must-haves should come first.
- A visual that doesn't match the lesson text is worse than none, so each visual is reviewed alongside its pill, and Gio reviews as the first learner.
- Mobile layouts need testing since drag interactions differ on touch.
